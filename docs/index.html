QGIS Live Driver (`geo_driver`)

Localhost-only remote control driver for QGIS (token-authenticated MCP/REST/file API for local AI tools) plus a built-in AI assistant panel for OpenAI-compatible APIs and a hot-reload watcher for plugin development

A control-only plugin with no UI that lets clients on the same PC (AI tools, etc.) remotely operate a running QGIS process. It can be installed standalone into any QGIS installation simply by copying it to python/plugins/ (no repository or Node required).

Because this plugin does not include QWebEngineView, any QGIS environment that does not use WebEngine, and any other plugin can also be provided with a pyeval-based remote control surface.

  • Commands: pyeval (arbitrary Python execution) / screenshot / status / open_plugin / reload_plugin / bridge_call + plugin_id forwarding (hub)
  • Connection surfaces (4 channels, all to the same dispatch): file JSONL / HTTP REST /api/* / MCP Streamable HTTP /mcp / MCP stdio (mcp_stdio.py)

Detailed documentation (command list, control scope, REST endpoints, etc.): https://yamamoto-ryuzo.github.io/qgis_live_harness/driver.html

Enabling

# From this repository (deploy all plugins at once)
powershell -ExecutionPolicy Bypass -File scripts/deploy-plugin.ps1 -Install

# Or manually: copy this folder to python/plugins/geo_driver/
# and enable it in the QGIS plugin manager

Quick start (first run)

  1. Install and enable the plugin (see above).
  2. Turn on Plugins > QGIS Live Driver > Remote Control (localhost only) and accept the warning; a Connection Info dialog opens automatically with all the information needed to connect (MCP URL, token, registry path, live dir). Afterwards you can reopen it at any time from Plugins > QGIS Live Driver > Connection Info.
  3. Paste the displayed settings into your MCP client:
    • stdio (recommended): starts the bundled mcp_stdio.py and auto-detects the running QGIS session, so no port/token configuration is needed.
    • Streamable HTTP: add the displayed Authorization: Bearer <token> to http://127.0.0.1:<port>/mcp.
    • Plain REST is also shown as a curl example.
  4. (Development only) To bind the plugin to the qgis_live_harness repository (required for Deploy Mode / hot reload), specify the repository folder via Select Harness repository… in the Connection Info dialog or, under Plugins > QGIS Live Driver > Deploy Mode, via Browse…. The path is saved to QSettings and takes precedence over marker/junction auto-detection.

Enabling has 2 routes (OFF and harmless by default):

  • Menu toggle: Plugins > QGIS Live Driver > Remote Control (localhost only). A warning dialog is shown the first time it is turned on, and the setting is saved to QSettings, so it is enabled automatically from the next launch.

This plugin also creates a GeoSuite shared toolbar and places a deploy-mode badge (always-visible development/usage mode indicator) at its head. Clicking it opens the Deploy Mode dialog. Toolbar items of other Harness-managed plugins (geo_search, etc.) are also consolidated into this toolbar.

  • Environment variable: when WEBENGINE_LIVE_DIR is set, it is enabled immediately at startup (for development; scripts/verify-in-qgis.ps1 sets it when launching).

AI assistant panel

Plugins > QGIS Live Driver > AI Assistant opens a chat dock that operates QGIS interactively by connecting to an LLM API (ai_panel.py + ai_client.py).

  • Providers (choose in the combo; settings are stored separately per provider. Each entry is prefixed with a connection-type tag [API]/[ACP]/[Bridge]):

    • OpenAI-compatible: Chat Completions (POST {base}/chat/completions + function calling). By changing the endpoint, local/compatible servers such as Ollama (http://localhost:11434/v1), LM Studio, OpenRouter, xAI Grok (https://api.x.ai/v1), Mistral, Groq and DeepSeek can also be used. Proprietary API families such as AWS Bedrock and Vertex AI can also be connected through an OpenAI-compatible proxy such as LiteLLM
    • Anthropic (Claude): Anthropic Messages API (POST {base}/v1/messages, tools = input_schema, auth via x-api-key + anthropic-version). Issue the API key at Anthropic Console. Default model claude-sonnet-4-5
    • Gemini: Google Gemini API (POST {base}/models/{model}:generateContent + functionDeclarations, auth via x-goog-api-key). Issue the API key at AI Studio. Default model gemini-2.5-flash
    • Azure OpenAI: Azure OpenAI Service Chat Completions ({resource}/openai/deployments/<deployment>/chat/completions ?api-version=…, auth via the api-key header). Put the deployment URL in the endpoint field and the deployment name in the model field. api-version defaults to 2024-10-21 when omitted
    • GitHub Copilot: OpenAI-compatible Copilot API (POST {api}/chat/completions). A GitHub Copilot subscription is required. Put a GitHub token (gho_/ghu_/ghp_…) in the API key field. Internally it is exchanged at api.github.com/copilot_internal/v2/token and sent to the endpoints.api (individual/business/enterprise) from the response. In environments where v2/token does not respond, it automatically falls back to resolving only the API target via copilot_internal/user and using the GitHub token as-is as a Bearer token (same behavior as the @github/copilot CLI). The "Sign in with GitHub" button can also obtain a token via the OAuth device flow (the default client_id is VS Code's public OAuth App; can be overridden with QGIS_LIVE_GITHUB_CLIENT_ID). If the endpoint is changed from the default, no token exchange is performed and the GitHub token is used as-is as Bearer, so compatible proxies such as copilot-api also work. Supported plans: Pro/Free/Business/Enterprise/EMU (Enterprise Managed Users; EMU is available when a Business/Enterprise seat is granted by the enterprise). For Business/Enterprise/EMU, endpoints.api returns api.business./api.enterprise.githubcopilot.com, which is resolved automatically through the same path. For EMU, PAT issuance may be restricted by corporate policy, so "Sign in with GitHub" (device flow) is recommended. Models disabled by your organization's Copilot model policy cannot be listed or used. Enterprise-side restrictions such as IdP conditional access cannot be bypassed by the app. Some models such as the GPT-6 family do not accept /chat/completions and are Responses API only (POST {api}/responses), but this is auto-detected and routed via supported_endpoints from GET /models (falling back from the model_not_supported error when unavailable)
    • Devin [Bridge]: a pseudo-provider that injects the instruction "delegate the actual work to Devin via the qgis_devin_* tools" into an OpenAI-compatible chat. The tool loop runs on the panel side as before. For the endpoint/API key/model, configure the OpenAI-compatible destination used by the delegating chat
    • GitHub Copilot [Bridge]: a pseudo-provider that injects "delegate the actual work to Copilot CLI via the qgis_copilot_* tools" into an OpenAI-compatible chat (same shape as Devin [Bridge])
    • Devin [ACP]: a provider that uses a Devin CLI (devin acp) session as the chat engine. Sends flow to session/prompt, and Devin itself runs the tool loop (geo_driver's /mcp is passed as an MCP server, so QGIS can also be operated from Devin via qgis_pyeval etc.). No API key required; it shares the IDE's Devin credentials (windsurf_api_key in credentials.toml). The endpoint field is the session's working directory (default: home). Conversation history is kept by Devin, so it becomes a continuing conversation equivalent to session/load. The stop button stops the turn with session/cancel
    • GitHub Copilot [ACP]: uses a GitHub Copilot CLI (copilot --acp --stdio) session as the chat engine. The mechanism is the same as Devin [ACP], and authentication uses the gh login on the CLI side (the API key field is not needed). The endpoint field is the session's working directory

  • Model selection: the model field is an editable combo. The adjacent "Fetch" button loads the list of available models from GET {base}/models (for Gemini, models that do not support generateContent are excluded). The list is grouped by type (text/image input, image generation, embedding, etc.), and each entry also shows its price (input/output, $/1M tokens). Prices prefer the pricing/modality/context_length returned by OpenRouter etc., and use a known price table for major models (reference values) when unavailable. When the default endpoint is used, a list of recommended models is shown before fetching. The type, price and context length of the selected model are also shown below the model field

  • Agents/skills (instruction files): extend behavior with 2 kinds of Markdown files:

    • ~/.qgis-live/agents/*.md — always-injected instruction files (role/policy). Selecting one in the panel's "Agent" combo injects its body into the system prompt. The "Edit" button lets you create/edit/delete them (multiple definitions can be switched; the selection is also remembered per chat)
    • ~/.qgis-live/skills/*.md — on-demand procedure files. Only a list of id + description (+use_when) is included in the prompt, and the model reads the body with open() from qgis_pyeval when the task applies (not always injected, so tokens are saved). Configuration is via the "Skills" row in the API settings — all entries are listed in the combo (no selection needed; everything is listed automatically), and created/edited/deleted in the "Edit" dialog
    • Both can ship plugin-bundled defaults under <plugin>/<kind>/, and user files with the same name take precedence. Format: the first # line = title, the next non-empty line = description, and the use_when: <when to use> line immediately after it (optional; aliases when/when_to_use/purpose/when to use) = activation condition, shown in the prompt list as use when: (bundled defaults are optional; there are currently none)
    • The AI itself can also edit/select instruction files: in addition to ai_list_instructions / ai_read_instruction / ai_save_instruction / ai_delete_instruction, ai_select_agent (switching the selected agent) is passed to the model. The agent list, like skills, appears in the prompt as id + description, so the model can autonomously select an agent that suits the task. Saves always write to the user side, and bundled files are effectively overwritten by saving with the same name (deletion applies to the user side only). After changes, the panel's combo is also rebuilt automatically
    • The "Edit" dialog is non-modal: the chat input remains usable as usual while it is open. Write a revision instruction in the prompt field at the bottom of the dialog and click "Ask AI to revise"; it is sent to the chat AI together with the body in the edit field, and the result saved by the AI with ai_save_instruction is reflected in the edit field (unsaved manual edits are not overwritten while present). If a file with the same name is saved while creating a new one, that file becomes selected
    • Can also be edited directly from the chat input: input starting with / is not sent to the API but executed as a local command. /agent (list + current value), /agent <name> (switch), /agent <name> <body> (save and select), /skill (list), /skill <name> (show body), /skill <name> <body> (save). The body can be written on the second line and beyond. /help shows the list
    • Can also be operated from external AI: the qgis_instruction tool on the MCP/REST side (op=list|read|save|delete) lets an orchestrator discover and edit instruction files (allowed via QGIS_LIVE_TOOLS)

  • Display: AI responses are rendered as Markdown (headings/lists/tables/ code blocks). "New chat" saves the current conversation to the history combo and starts a new one. Opening a past chat from the history combo restores the display and context so the conversation can continue. History is persisted to ~/.qgis-live/chats.json (latest 50) and survives a QGIS restart. "↓" saves the displayed chat as Markdown, and "✕" deletes the displayed history chat

  • Send/stop/resend: send with Enter (or "Send"), newline with Shift+Enter. While the input is empty, "Send" is disabled, and while running the button turns into a red "■ Stop" so that the loop can be stopped at a round-trip boundary (in-flight API responses and tool executions themselves are allowed to finish). "Resend" cancels the last question + response and sends the same question again. Long conversations are automatically trimmed from the oldest turns (MAX_HISTORY_CHARS) so an oversized context does not cause API errors. Context/cost indicator at the bottom right (ctx 9k/128k (6%) · Σ13k · $0.0023). ctx is the measured prompt_tokens of the most recent API response (estimated as characters÷3 with ~ when unavailable), Σ is cumulative tokens per chat, and $ is the estimated cost for models with price information (for flat-rate Copilot etc., only Σ is shown). Saved to chat history along with usage

  • Image attachment: attach images by pasting into the input (Ctrl+V), dragging & dropping image files, or the "📎" button. They line up as thumbnail chips above the input and are bundled into the user message on send (they remain in history and can also be referenced by the model in later turns). Images are normalized to PNG and resized to a long edge of 2048px, then saved to a temp file. While a model estimated not to support images is selected (outside the "image input" group in the list), attachment is not possible, and the 📎 button is also disabled (manually entered models are estimated from name hints)

  • Confirmation mode: turning on "Confirm before tool execution" asks for approval each time a tool is called (for when you do not want pyeval arbitrary code execution to run automatically)

  • Tools: the same set as mcp_http.TOOLS (qgis_pyeval / qgis_screenshot / qgis_status / qgis_eval / qgis_devreload / qgis_open_plugin / qgis_reload_plugin / qgis_bridge_call / qgis_instruction / qgis_devin_* / qgis_copilot_*), plus panel-local tools ai_* for reading and writing instruction files, and tools mcp_* from external MCP servers, are passed to the model, and returned tool_calls are processed with driver.submit() (for qgis_) or local execution (ai_/mcp_*) in an agent loop (max 25 round trips)

  • External MCP server connection: API settings "MCP" row → "Configure" edits ~/.qgis-live/mcp_servers.json (Claude Desktop-compatible format):

    {"mcpServers": {
  "fs":  {"command": "npx",
          "args": ["-y", "@modelcontextprotocol/server-filesystem", "C:/work"]},
  "api": {"url": "http://localhost:3000/mcp",
          "headers": {"Authorization": "Bearer ..."}},
  "box": {"url": "https://mcp.box.com",
          "oauth": {"authorize_url":
                      "https://account.box.com/api/oauth2/authorize",
                    "token_url": "https://api.box.com/oauth2/token",
                    "client_id": "...", "client_secret": "...",
                    "redirect_uri": "http://127.0.0.1:8020/callback"}},
  "ccg": {"url": "https://example.com/mcp",
          "oauth": {"token_url": "https://example.com/oauth/token",
                    "client_id": "...", "client_secret": "...",
                    "extra": {"box_subject_type": "enterprise",
                              "box_subject_id": "..."}}}
}}

    command = launch a child process over stdio (no console window on Windows), url = Streamable HTTP. Secrets go to the credential store: saving a plaintext value in oauth.client_secret automatically moves it to the OS credential store (credential_store; the same location as API keys), and only a "$store:mcp:<server>:client_secret" reference remains in the config file. If storing to the store fails, an error occurs and nothing is saved in plaintext. Values of headers/env/oauth.client_id can also be written as "$store:<key>" and are resolved from the store at connect time (writing references manually requires pre-registering them in the credential store). Existing configs that still contain a plaintext client_secret are migrated when re-saved in the settings dialog. Authentication either passes fixed values via headers or uses 2 kinds of OAuth via oauth: with authorize_url = authorization_code+PKCE (a browser opens on the first send for a consent screen; the token is saved to ~/.qgis-live/mcp_tokens.json and afterwards refreshed automatically with refresh_token; for user-consent servers such as mcp.box.com; redirect_uri must be registered in the app), without authorize_url = client_credentials (client_id+secret, with extra for provider-specific form parameters). Retries once on 401. On connection failure, a checklist guide "①Register the Redirect URI ②enable authorization_code ③id/secret match" is shown together with the error. To use mcp.box.com, additionally a Business plan or higher on the Box side, enabling MCP in the Admin Console, and standard OAuth2 with a Custom App (a CCG-only Server App does not work) are required. The obtained token is saved in plaintext to ~/.qgis-live/mcp_tokens.json (handle with care since it contains access/refresh tokens). On the first send, connection and tools/list are performed, and each tool is exposed to the model as mcp_<server>__<tool>. Saving settings reconnects on the next send. Servers that fail to connect are shown with an error in the chat area while other servers continue. Note: pointing at QGIS's own driver MCP endpoint makes tools/call go through GUI thread dispatch, creating a self-reference, so in practice point at another server

  • Works even when the remote control toggle is OFF: it uses a panel-private internal LiveDriver (no registry or HTTP exposure), so AI operations alone can be tried without enabling external exposure

  • Image sending: results of qgis_screenshot are image_url content, and attached images (paste/📎) are bundled into the user message and sent to the model as images. With models estimated not to support images, screenshot results are returned as text (path) only, and attachment itself is not possible

  • Settings (endpoint/model) are saved to QSettings. API keys are saved to the OS credential store (credential_store.py): Windows uses DPAPI (user-bound encryption like browser password storage), macOS the Keychain, Linux Secret Service (secret-tool). Only when none is available does it fall back to ~/.qgis-live/ai-secrets.json (mode 600, plaintext). The current backend can be checked in the panel's "Key storage" field. If writing to the store itself fails, an error is shown and nothing is saved in plaintext

Security model (localhost only)

Because pyeval allows arbitrary code execution, all channels are protected as follows:

  • 127.0.0.1 binding only — unreachable from external networks
  • Session token required — auto-generated on each launch. HTTP compares Authorization: Bearer etc., and commands.jsonl compares the token field of each line. The token is written only to ~/.qgis-live/<pid>-geo_driver.json (registry) and live_dir/token, with user-only ACLs applied
  • Host/Origin validation — HTTP requests whose Host or Origin points anywhere other than loopback are rejected (protection against DNS rebinding and browser-based drive-by)
  • QGIS_LIVE_TOOLS can restrict the exposed command types (e.g. status,screenshot)

Threat model boundary: because the token is placed in a user-only file, processes that can execute arbitrary code with the same user privileges cannot be prevented (this is the limit of any localhost service). The trust boundary is the local user account.

Local MCP clients (such as mcp_stdio.py) read the token from the registry automatically, so the usage procedure does not change.
